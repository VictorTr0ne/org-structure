┌─────────────────────────────────────────────────────────────────┐

│                                и рассылает патч всем WS-клиентам │

└─────────────────────────────────────────────────────────────────┘
                    │ HTTP GET (JSON)         │ WebSocket (JSON-патчи)
                    ▼                          ▼
┌─────────────────────────────────────────────────────────────────┐

│  1. schema/        — Zod-валидация ответа API и WS-патчей       │
│  2. query/          — useQuery: кэш + stale-while-revalidate     │
│  3. tree/           — buildTree: плоский список -> дерево        │

                    │
                    ▼
┌─────────────────────────────────────────────────────────────────┐

│  Dashboard  — единственный держатель состояния и оркестрация:    │

## Поток данных

1. **Первая загрузка.** `useOrgTreeQuery` запрашивает `GET /api/org-tree`
   через кэш-слой (`useQuery`, stale time 5с). Ответ валидируется схемой
   Zod (`orgNodeSchema`) — при несовпадении бросается `OrgTreeValidationError`,
   которую `Dashboard` превращает в состояние ошибки с кнопкой «Повторить».
2. **Гидратация.** По первому успешному ответу `Dashboard` строит статичную
   структуру дерева (`buildTree`) и снимок значений (`collectInitialValues`),
   затем считает агрегаты один раз (`aggregateTree`, `useMemo`-подобно —
   через `useEffect`, срабатывающий один раз на `!treeRef.current`).
   Структура дерева (id/parentId/children/depth) после этого не пересчитывается —
   меняются только «значения» узлов и агрегаты.
3. **Live-обновления.** `useOrgTreeSocket` держит WebSocket-соединение к `/ws`.
   На каждый входящий патч `Dashboard`:
   - обновляет `values` точечно (без рефетча и без перестроения дерева);
   - вызывает `applyPatchToAggregates`, который трогает только сам узел и
     цепочку предков (`getAncestorIds`), а не весь агрегатный стор;
   - включает fade-подсветку изменившихся полей на 1.5с.
4. **Рендер.** `OrgTree` рекурсивно рисует узлы из статичной структуры,
   беря текущие значения по id. `OrgTable` строит плоский список строк
   (`useTableRows`), применяет debounce-фильтр/AI-поиск и сортировку,
   не трогая исходные `values`/`aggregates`.
5. **Взаимодействие.** Клик по строке таблицы (`onSelectNode`) обновляет
   `selectedId` и раскрывает предков узла в дереве; клик по узлу дерева
   переключает `expandedIds`.

## Почему состояние живёт в одном компоненте (Dashboard)

Дерево, таблица и шапка — разные проекции одних и тех же данных (`values`,
`aggregates`, `selectedId`). Поднимать это состояние в контекст или
глобальный стор избыточно при одном экране приложения; проп-дриллинг на
глубину в 2–3 уровня явнее и проще для ревью, чем скрытая связь через
контекст. Если бы в приложении появился второй экран с орг-структурой,
это стало бы поводом вынести состояние в контекст — на объём текущего
задания это была бы преждевременная абстракция.
