# Модель данных

## OrgNode (контракт `GET /api/org-tree`)

```ts
interface OrgNode {
  id: string;
  name: string;
  parentId: string | null; // null только у корней (дивизионов)
  headcount: number;       // собственная численность узла, >= 0
  budget: number;          // собственный бюджет узла, >= 0
  performance: number;     // 0..100
  updatedAt: string;       // ISO-строка
}
```

Ответ — плоский массив ≥40 узлов, минимум три уровня вложенности:
дивизион (`parentId: null`) → отдел → команда. Валидируется на клиенте
схемой `orgNodeSchema` (`client/src/lib/schema/orgNode.ts`); невалидный
ответ (например, `performance: 150` или отсутствующее поле) приводит к
`OrgTreeValidationError`, а не к отрисовке мусора.

Важно: **каждый** узел (не только листья) несёт собственные
headcount/budget/performance — так суммирование по поддереву на каждом
уровне не тривиально (дивизион = свой аппарат + все отделы и команды).

## Построение дерева

`buildTree(nodes: OrgNode[])` (`client/src/lib/tree/buildTree.ts`):

1. Создаёт `Map<id, TreeNode>`, где `TreeNode = OrgNode & { depth, children }`.
2. Раскладывает узлы по `parentId`: узел без родителя или с несуществующим
   `parentId` считается корнем (не отбрасывается — так на любую проблему
   целостности данных сервера UI отреагирует лишним корнем, а не пустым деревом).
3. Обходом от корней проставляет `depth`, начиная с 1.

Эта структура строится **один раз**, при первой успешной загрузке, и не
пересчитывается при live-патчах — патчи меняют только значения полей
конкретных узлов, а не форму дерева.

## Агрегация

### Полный проход (`aggregateTree`)

Для каждого узла считается свёртка по поддереву, включая сам узел:

```ts
interface SubtreeAggregate {
  totalHeadcount: number;        // сумма headcount узла и всех потомков
  totalBudget: number;           // сумма budget узла и всех потомков
  performanceWeightSum: number;  // сумма performance_i * headcount_i по поддереву
}
```

Средняя эффективность, взвешенная по headcount, — производная величина:
`weightedPerformance = performanceWeightSum / totalHeadcount`
(при `totalHeadcount === 0` — берётся собственная performance узла, чтобы
не делить на ноль и не терять сигнал у пустых по численности узлов).

Считается один раз после загрузки дерева и хранится в `Map<id, SubtreeAggregate>`
(`Dashboard` вызывает это в `useEffect` при первой гидратации, не на
каждый рендер).

### Инкрементальный пересчёт (`applyPatchToAggregates`)

При live-патче пересчитывать всё дерево незачем — экономически он
меняет headcount/budget/performance одного узла. Функция:

1. Считает дельты: `Δheadcount`, `Δbudget`,
   `Δ(performance*headcount)` между старым и новым значением узла.
2. Идёт по цепочке `[nodeId, ...предки]` (`getAncestorIds`) и прибавляет
   дельты к уже посчитанным агрегатам — **не трогая** агрегаты
   несвязанных узлов (соседних команд, других дивизионов).

Тест `aggregateTree.test.ts` проверяет, что результат инкрементального
пути идентичен полному пересчёту `aggregateTree` после того же изменения —
это гарантия, что оптимизация не разошлась с эталонной формулой.

## Контракт WebSocket-патча

Канал: `ws(s)://<host>/ws` (в dev — проксируется Vite, в проде — Nginx).
Формат сообщения (JSON), валидируется `orgNodePatchSchema` на клиенте:

```ts
interface OrgNodePatch {
  type: "update";
  nodeId: string;
  changes: {
    headcount?: number;
    budget?: number;
    performance?: number;
    updatedAt: string; // всегда присутствует
  };
}
```

- `changes` содержит **хотя бы одно** из трёх метрик (сервер меняет
  ровно одно поле за раз) плюс новый `updatedAt`.
- Патч всегда адресован существующему `nodeId`; клиент, получив патч на
  неизвестный id (не должно происходить, но защитно обрабатывается),
  просто игнорирует его.
- Один нераспарсенный/невалидный фрейм не рвёт соединение — `useOrgTreeSocket`
  просто пропускает его и ждёт следующий.
