# ADR 003 — Локальный эвристический парсер вместо вызова LLM API для AI-поиска

## Контекст

Bonus-этап просит строку поиска, принимающую естественный язык, с
ответом в виде структурированного фильтра на клиенте и текстовым
поиском как fallback. Очевидный способ — отправлять запрос в реальный
LLM API (например, Claude) и парсить JSON-ответ.

## Решение

Реализован локальный эвристический парсер
(`client/src/lib/aiSearch/parseQuery.ts`): регулярные выражения по
русским словоформам («дивизион/отдел/команда», «сотрудник/численность»,
«бюджет», «эффективность») плюс операторам сравнения («больше», «меньше»,
«не менее», «не более») и числам с суффиксами «млн»/«тыс». Результат —
`StructuredFilter { level?, headcount?, budget?, performance? }`.
Если парсер не распознаёт запрос, `Dashboard`/`OrgTable` откатываются к
обычному подстроковому поиску по названию — то есть к поведению,
которое и так требуется на этапе CORE.

## Причины отказа от реального LLM-вызова

- **Секреты в тестовом артефакте.** Реальный вызов потребовал бы
  `ANTHROPIC_API_KEY` (или аналог) в `.env`, который нельзя закоммитить
  в публичный репозиторий тестового задания — а без него bonus-фича
  на чужой машине просто не работала бы «из коробки».
- **Сетевая зависимость и стоимость на каждый ввод пользователя.**
  Даже с debounce каждый новый вариант фразы — отдельный внешний вызов
  с задержкой и стоимостью; для демонстрационного дашборда это
  несоразмерная плата за поиск по 50–60 строкам. В реальном продукте
  с кэшированием частых запросов это приемлемый компромисс, но не для
  тестового окружения без бэкенд-прокси к LLM.
- **Достаточность эвристики для заявленного набора фильтров.** Число
  полей, по которым в принципе можно фильтровать (headcount/budget/
  performance/level), фиксировано и невелико — правило-ориентированный
  парсер покрывает практический диапазон формулировок без риска
  галлюцинации несуществующего поля.

## Альтернативы

- **Вызов Claude API с сервера** (чтобы не светить ключ на клиенте) —
  архитектурно самый корректный путь для реального продукта: строка
  запроса шла бы на `POST /api/search/interpret`, сервер вызывал бы LLM
  и возвращал строгий JSON-фильтр по схеме. Явно оставлено как
  расширение — интерфейс `parseNaturalLanguageQuery(query): StructuredFilter | null`
  спроектирован так, что его реализацию можно заменить на такой вызов,
  не трогая `OrgTable`/`useTableRows`.
- **Без AI вовсе, только текстовый поиск** — не выполняет требование
  bonus-этапа буквально.

## Последствия

- Парсер понимает только заранее заданный, пусть и достаточно широкий,
  набор формулировок (см. тесты в `parseQuery.test.ts`); нестандартные
  фразы уходят в fallback на текстовый поиск, а не возвращают ошибку —
  это осознанный компромисс в пользу предсказуемости для пользователя.
- Замена на реальный LLM-вызов в будущем — это подмена одной функции
  (`parseNaturalLanguageQuery`) на асинхронный вызов сервера, без
  изменений в остальном коде таблицы.
