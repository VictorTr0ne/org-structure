# ADR 001 — Собственный stale-while-revalidate хук вместо react-query/swr

## Контекст

Задание требует кэширования ответа `GET /api/org-tree` с stale time 5с,
избегания лишних запросов и корректной отмены запроса при размонтировании.
Стандартное решение — `@tanstack/react-query` или `swr`. Но:

- В приложении **один** реальный запрос (`/api/org-tree`); живые обновления
  идут отдельным WebSocket-каналом, а не через рефетч. Полноценный
  query-клиент с инвалидацией по ключам, ретраями, garbage collection —
  функциональность, которая в этом проекте не используется.
- Bonus-этап требует production-бандл ≤200 КБ gzip; react-query добавляет
  заметный вес, который не окупается на один эндпоинт.
- Часть смысла задания — показать, что stale-while-revalidate понимается
  как паттерн, а не только как опция библиотеки.

## Решение

Реализован `useQuery` (`client/src/lib/query/useQuery.ts`) — минимальный
хук на `useSyncExternalStore` с модульным кэшем по ключу:

- отдаёт закэшированные данные немедленно, если они моложе `staleTime`;
- если данные устарели — фоново перезапрашивает, но не сбрасывает то,
  что уже показано (SWR-поведение);
- дедуплицирует параллельные запросы на один и тот же ключ;
- аварийно отменяет запрос (`AbortController`) при размонтировании
  компонента-потребителя.

## Альтернативы

- **react-query/swr** — отклонено из-за веса и избыточности для одного
  эндпоинта (см. выше).
- **Просто `useEffect` + `fetch` без кэш-слоя** — не удовлетворяет
  явному требованию "запрос через слой кэширования, stale time 5 секунд";
  также не решает дедупликацию при нескольких потребителях одного ключа.

## Последствия

- Меньше кода и веса бандла, но кэш-слой не имеет функций, которых в
  проекте и не требуется (ретраи с backoff на HTTP-запросах, garbage
  collection неиспользуемых ключей, оптимистичные обновления). Если в
  будущем появится больше запросов с более сложной инвалидацией —
  стоит пересмотреть это решение в пользу зрелой библиотеки.
