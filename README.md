# Org Dashboard

Дашборд для мониторинга орг-структуры компании: интерактивное дерево
(дивизион → отдел → команда) и аналитическая таблица с агрегированными
показателями, живыми обновлениями по WebSocket и поиском на естественном
языке.

## Стек

- **Клиент**: React 19, TypeScript, Vite, styled-components, Zod (валидация
  ответа API).
- **Сервер**: Node.js, Express, `ws` (WebSocket), без БД — данные в памяти.
- **Тесты**: Vitest.
- **Прод-инфраструктура**: Docker, Nginx.

## Запуск

### Локально, одной командой

Требуется Node.js ≥20.19 или ≥22.12 (Vite использует `node:util`'s
`styleText`, которого нет в более старых Node 20.x — например, в
20.10/20.11). В репозитории есть `.nvmrc`; если используете nvm:

```bash
nvm use   # или: nvm install 22 && nvm use 22
```

```bash
npm install
npm run dev
```

`npm run dev`/`build`/`test` сами проверяют версию Node и сразу
выводят понятную ошибку вместо непонятного `SyntaxError` из Vite,
если версия слишком старая.

Поднимает сервер на `http://localhost:3001` и клиент на `http://localhost:5173`
(Vite-прокси перенаправляет `/api` и `/ws` на сервер). Открыть
`http://localhost:5173`.

Отдельно: `npm run dev:server`, `npm run dev:client`.

### Через Docker

Требуется Docker и Docker Compose.

```bash
cp .env.example .env
docker compose up --build
```

Клиент (через Nginx, со сжатием и проксированием `/api`/`/ws`) будет
доступен на `http://localhost:${CLIENT_PORT:-8080}`.

> Собственная проверка: Docker-конфигурация (`client/Dockerfile`,
> `server/Dockerfile`, `docker-compose.yml`, `nginx/nginx.conf`) написана
> и вычитана вручную, но **не запускалась** — в среде, где готовился этот
> репозиторий, не было доступа к Docker-демону. Перед сдачей стоит
> прогнать `docker compose up --build` локально.

## Тестирование

```bash
npm run test          # Vitest: агрегация, построение дерева, форматирование, AI-парсер
npm run build         # прод-сборка клиента + отчёт о размере gzip-бандла
```

### Ручной сценарий проверки (в браузере)

1. **Загрузка.** Открыть приложение — дерево должно раскрыться на уровень
   дивизионов (второй уровень, отделы, виден сразу), с цветным индикатором
   эффективности (зелёный ≥80, жёлтый 50–79, красный <50) и численностью
   у каждого узла.
2. **Дерево.** Клик по стрелке разворачивает/сворачивает ветку с плавной
   анимацией высоты (в системных настройках с "уменьшить движение"
   анимация отключается).
3. **Переключение видов.** При ширине окна <1280px — переключатель
   «Дерево / Таблица»; при ≥1280px оба показаны рядом (split-view), а
   переключатель скрывается.
4. **Таблица.** Проверить колонки (Подразделение, Уровень, Всего
   сотрудников, Бюджет суммарный, Средняя эффективность), формат бюджета
   (`12 345 678 руб.`), сортировку кликом по заголовку (по возрастанию) и
   двойным кликом (обратный порядок).
5. **Фильтр.** Ввести обычное слово (например, «продаж») — таблица
   фильтруется в реальном времени с задержкой ~250мс. Затем ввести фразу
   на естественном языке, например:
   - `команды с бюджетом больше 5 млн`
   - `дивизионы с эффективностью больше 50`
   - `отделы с численностью не более 10`

   Под полем ввода появится подсказка «Распознан фильтр: …». Для фразы,
   которую парсер не распознал (например, случайное слово), сработает
   обычный текстовый поиск по названию.
6. **Выбор строки.** Клик по строке таблицы выделяет и раскрывает путь
   до соответствующего узла в дереве.
7. **Live-обновления.** Подождать 3–8 секунд — в шапке индикатор
   соединения показывает «Онлайн»; какая-то ячейка в таблице (headcount,
   бюджет или эффективность одной из команд, а также агрегаты её отдела и
   дивизиона) на ~1.5 секунды подсветится и погаснет — это применённый
   WebSocket-патч без полного перезапроса дерева. Чтобы проверить
   переподключение — остановить сервер (`Ctrl+C` в терминале с
   `npm run dev:server`) и посмотреть, как индикатор переходит в «Нет
   соединения» и пытается переподключиться с увеличивающейся паузой;
   затем перезапустить сервер — соединение восстановится.
8. **Клавиатурная навигация.** Кликнуть по строке таблицы (чтобы дать ей
   фокус), затем использовать стрелки вверх/вниз, Home/End и Enter —
   фокус двигается по строкам, Enter выделяет строку и раскрывает её в
   дереве.
9. **Состояния.** Отключить сеть/остановить сервер до первой загрузки —
   должен показаться экран ошибки с кнопкой «Повторить».

### Что покрыто тестами, а что — нет

Модульными тестами (Vitest) покрыта вся логика без DOM: агрегация
(полная и инкрементальная — с явным сравнением результатов друг с другом),
построение дерева из плоского списка, форматирование валюты,
эвристический AI-парсер. React-компоненты не покрыты
unit/RTL-тестами — вместо этого поведение UI проверено вручную в браузере
(см. сценарий выше); при развитии проекта в первую очередь стоило бы
добавить interaction-тесты для `OrgTable` (сортировка, клавиатурная
навигация) и `Dashboard` (применение WS-патча).

## AI в разработке

Код в этом репозитории написан через Claude Code как основной
инструмент генерации — но не «нажал кнопку и получил результат»:
архитектурные решения на развилках, приёмка плана перед реализацией и
тестирование каждого этапа вживую (в браузере и на своей машине) были
моими, и именно на этом этапе всплыла часть проблем, которые ни
генерация, ни автотесты сами не поймали бы. Ниже — конкретные решения,
конкретные баги и то, кто их нашёл.

### Решения, принятые явно, не по умолчанию

- **Локальный эвристический AI-поиск вместо вызова внешнего LLM API.**
  Перед реализацией мне предложили выбор — вызывать реальный LLM
  (Claude API) с сервера или разбирать запросы локальными правилами.
  Выбрал локальный вариант: без ключей/секретов в тестовом репозитории
  и без сетевой задержки на каждый символ ввода. Обоснование — в
  [docs/adr/003-ai-search-approach.md](docs/adr/003-ai-search-approach.md).
- **Отдельный репозиторий, не подкаталог существующего проекта.**
  Стек и назначение не пересекались с моим текущим проектом (там Vue),
  поэтому попросил вынести дашборд в независимый git-репозиторий.

### Баги, которые нашёл я сам, руками тестируя приложение

- **`npm run dev` падал на моей машине.** Дефолтная версия Node через
  nvm (20.10.0) оказалась слишком старой для тулчейна Vite (`node:util`'s
  `styleText`, есть только с 20.12+/22.12+) — вместо понятной ошибки
  падал `SyntaxError` глубоко внутри rolldown. По моему репорту добавлены
  `.nvmrc`, `engines` в `package.json` и guard-скрипт
  (`scripts/check-node.mjs`), который теперь сразу и понятно
  останавливает `dev`/`build`/`test` на несовместимой версии Node.
- **AI-поиск по буквальному названию узла ломался.** Ввёл в поиск
  «Команда автотестов» (реальное имя команды) — вместо неё показались
  все команды подряд: парсер распознавал слово «команда» как фильтр по
  уровню и молча отбрасывал «автотестов». Поправлено в
  [`client/src/lib/aiSearch/parseQuery.ts`](client/src/lib/aiSearch/parseQuery.ts) —
  теперь фильтр по уровню срабатывает, только если после него нет
  содержательного остатка текста или явно есть числовое условие
  (бюджет/эффективность/численность), иначе запрос уходит в обычный
  текстовый поиск.

### Баги, найденные при собственной проверке Claude Code в браузере (Playwright)

- **Кэш-слой (`client/src/lib/query/useQuery.ts`) вешал дашборд на
  «Загружаем…».** Дедупликация запросов флагом «идёт ли уже фетч»
  сталкивалась с двойным вызовом эффектов в React StrictMode (dev-режим):
  один и тот же ключ монтировался, размонтировался и монтировался
  заново за один тик, второй запрос блокировался дедупликатором,
  который ещё не знал, что первый уже отменён. `runFetch` и
  cleanup-эффект переписаны так, чтобы cleanup немедленно освобождал
  блокировку при отмене.
- **Подсказка AI-поиска показывала сырые коды операторов** —
  `бюджет gt 5 000 000 руб.` вместо «больше 5 000 000 руб.». Код был
  рабочим, но нечитаемым; добавлена таблица перевода
  `gt/gte/lt/lte` → «больше/не менее/меньше/не более» в
  `client/src/components/OrgTable/OrgTable.tsx`.

### Проверка типов после генерации

`tsc -b` несколько раз ловил то, что генерация сама не учитывает:
`noUncheckedIndexedAccess` требовал явных утверждений типа при
обращении по индексу массива (`server/src/data/generateOrgTree.ts`,
`server/src/realtime/broadcaster.ts`), а `erasableSyntaxOnly` запретил
TS-специфичные parameter properties в конструкторе
`OrgTreeValidationError` (`client/src/lib/schema/orgNode.ts`) —
пришлось заменить на обычное поле класса с явным присваиванием в
конструкторе. Оба случая — несовпадение сгенерированного кода со
строгими опциями компилятора, заданными в этом же проекте, а не
«ИИ написал неверный код»; правки внесены по сообщениям `tsc`, а не
переписыванием вслепую.

### Что сгенерировано и не менялось

`server/src/data/generateOrgTree.ts` и Zod-схемы (`client/src/lib/schema/*`) —
механическая часть (генератор тестовых данных, описание контракта),
где ручная правка не добавляла бы ценности. Аналогично
`docs/adr/*`, `docs/architecture.md` и `docs/data-model.md` —
задокументированы по итогам уже принятых решений, а не диктовали их.
Корректность инкрементальной агрегации
(`client/src/lib/aggregation/incremental.ts`) принята не на глаз:
`aggregateTree.test.ts` явно сравнивает результат инкрементального
патча с результатом полного пересчёта `aggregateTree` на тех же
данных — тест проверяет эквивалентность двух независимых путей
вычисления, а не просто фиксирует ожидаемые числа снимком.

Формулировки самого технического задания (PDF) проверены на признаки
вредоносности/prompt injection перед началом работы — файл оказался
обычным заданием без скрытых инструкций.
